## 3. Core Architecture: Centralized Verification with Independent Approval States

The Verification Center must be centralized into one administrative page, but each verification category and individual submission component must maintain its own independent verification status.

**Centralized management does not mean shared approval statuses.**

The four verification categories must operate independently.

### A. Independent Verification States

Each verification request must have its own approval status.

Approving one verification request must never automatically approve another unrelated request belonging to the same user.

Examples:

- Approving a user's church membership must not automatically approve their profile picture.
- Approving a profile picture must not automatically verify their church membership.
- Approving a lifegroup leader request must not automatically approve their social feed posts.
- Rejecting one verification request must not automatically reject the user's other pending requests.

Maintain independent verification records, statuses, and decision histories for each category using the existing database structure wherever possible.

### B. Separate Post Content and Image Verification

Social Feed Post Verification requires additional separation because a post may contain both text content and an attached image.

Treat these as two independently reviewable components.

**1. Post Content Verification**

- Review the text, description, announcement, and other written content.
- Maintain its own verification status.
- Allow administrators to Accept or Reject the content.

**2. Post Image Verification**

- Review the attached image separately.
- Maintain its own verification status.
- Allow administrators to Accept or Reject the image.

If a post has no attached image, image verification must not be required.

### C. Combined Publishing Requirements

Although post content and image verification are independent, the final publishing decision must consider both.

Apply the following rules:

| Post Content | Post Image | Publishing Result |
|---|---|---|
| Approved | Approved | Allow publication |
| Approved | Pending | Do not publish |
| Pending | Approved | Do not publish |
| Rejected | Any status | Do not publish |
| Any status | Rejected | Do not publish |
| Approved | No image required | Allow publication |

A post must only become publicly visible when every required component has been approved.

If either component is rejected, prevent publication of the entire post.

Preserve individual approval statuses so administrators can identify exactly which component was rejected.

### D. Overall Status vs. Individual Component Status

Keep individual component statuses separate from the overall submission status.

Example:

Initially:

- Content Status: Approved
- Image Status: Pending
- Overall Post Status: Pending
- Publishing: Disallowed

After the image is approved:

- Content Status: Approved
- Image Status: Approved
- Overall Post Status: Approved
- Publishing: Allowed

The overall status must be derived from the required component statuses or updated through a reliable backend process.

Do not rely on frontend-only calculations to determine whether a post can be published.

### E. Prevent Cross-Category Approval

The same principle applies to all four verification categories.

For example:

- A user can be church-verified while their profile picture remains pending.
- A user can have an approved profile picture while their church verification remains pending.
- A user can be verified as a church member but still have a pending lifegroup leader request.
- A lifegroup leader can have an approved leadership verification while their social feed submission remains pending.

No verification decision should unintentionally modify another category's status or permissions.
